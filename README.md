# RecoGo — Product Recommendation Service

Учебный сервис рекомендаций товаров на Go. Собирает просмотры и покупки, строит item-to-item модель, выдаёт персональные рекомендации через HTTP API, автоматически переобучает модель и поддерживает откат версии.

**Начните с START_HERE_RU.md.** Для Windows приложен готовый исполняемый файл: `start_local.bat` запускает сервер, загружает демонстрационные события, обучает модель и открывает панель. Python и Go для такого запуска не требуются.

## Стек

| Задача | Реализация |
|---|---|
| API и бизнес-логика | Go, стандартный net/http |
| Сбор событий | Kafka, kafka-go; прямой локальный приём без брокера |
| События и реестр моделей | bbolt, транзакции, отдельный индекс по пользователю |
| Рекомендации | взвешенное item-to-item cosine similarity, popular fallback |
| Эксперименты | MLflow через REST API из Go, модели и отчёты как JSON-артефакты |
| Обновление | встроенный Go-планировщик; Kubernetes CronJob или опциональный Airflow |
| Поставка | готовые бинарники, Docker Compose, Kubernetes |
| Проверки | Go tests, race detector, vet, CI GitHub Actions |

Python/FastAPI заменены Go API. Airflow остаётся отдельным опциональным инструментом: его небольшой Python DAG только вызывает API, не реализуя расчёт рекомендаций.

## Что реализовано

- `POST /events` принимает view/purchase с идентификатором события.
- В Kafka-режиме API подтверждает запись в брокер кодом 202, consumer сохраняет событие до commit offset.
- Повторное событие с тем же содержимым не дублируется; конфликт event_id отклоняется. Невалидные сообщения consumer отправляет в DLQ перед commit.
- Модель учитывает покупки с весом 4, просмотры с весом 1; пользовательские суммы преобразуются log1p.
- Item-to-item similarities строятся по общим взаимодействиям пользователей. Для расчёта берутся последние 100 событий пользователя, хранится до 50 соседей товара.
- Уже встречавшиеся пользователю товары из его последних 100 событий исключаются; при нехватке персональных вариантов выдаются популярные. Более старые товары могут появиться снова.
- Хронологические 80/20 train/holdout, HitRate@5 и сравнение с популярностью.
- Минимум пользователей в оценке и проверка ухудшения относительно текущей модели на новых фактах. Неудачный кандидат не публикуется.
- Переключение активной модели: транзакция на диске, затем атомарная замена указателя в памяти.
- Ручное переключение на сохранённую версию. При повреждении активного артефакта на старте автоматически выбирается последняя валидная сохранённая модель.
- Контроль SHA-256 артефактов, журналирование JSON, метрики Prometheus, веб-панель.

## Быстрый запуск из исходников

Нужен Go 1.23 или новее. В двух терминалах:

```bash
go mod download
go run ./cmd/recogo serve
```

```bash
go run ./cmd/recogo seed
go run ./cmd/recogo train
curl "http://127.0.0.1:8080/recommendations?user_id=user-001&limit=5"
```

Открыть http://127.0.0.1:8080. Для административных кнопок введите `recogo-local`, если токен не меняли.

## Полный Docker-режим

```bash
docker compose up --build -d --wait api
docker compose exec -T api /recogo seed --url http://127.0.0.1:8080
docker compose exec -T api /recogo train --url http://127.0.0.1:8080
```

Панель: http://127.0.0.1:8080. MLflow: http://127.0.0.1:5000. В этом режиме события проходят Kafka, а Go вызывает MLflow REST API. MLflow — система трекинга; активная версия для serving хранится в локальном реестре bbolt.

## Версии и откат

```bash
go run ./cmd/recogo train
go run ./cmd/recogo rollback
go run ./cmd/recogo rollback --version VERSION_ID
```

Без `--version` выбирается ближайшая более старая валидная версия. До первого отката нужно создать хотя бы две принятые версии. Повторное обучение на том же наборе создаёт новую версию; сравнение с champion выполняется только при достаточном количестве новых оценочных покупок.

## Проверки и CI

```bash
go vet ./...
go test -race -cover ./...
go build ./cmd/recogo
```

CI проверяет Go-код, затем запускает Compose и сценарий Kafka → сохранение событий → обучение → выдача → повторное обучение → откат. Workflow выполнится после загрузки проекта в GitHub; наличие файла CI не означает, что полный стенд уже проверен. Фактически выполненные здесь проверки перечислены в `docs/VERIFICATION_RU.md`.

## Ограничения

Это учебный проект с синтетическими данными. Архитектура рассчитана на один экземпляр сервиса: bbolt допускает один процесс-владелец, Kubernetes Deployment использует `replicas: 1` и стратегию Recreate. Kafka запускается одним брокером и не обеспечивает отказоустойчивый кластер. Лимит — 100 000 сохранённых событий. Нет каталога наличия/цен, бизнес-фильтров, A/B-теста и доказанного highload/SLA. Score — ранжирующая оценка, не вероятность покупки.

Автоматический откат реализован при повреждении модели на старте. Автоматическая защита от снижения offline-качества отклоняет новую версию до публикации. Автоматический откат по онлайн-конверсии не реализован: для него нужны достоверная обратная связь, эксперимент и пороги.

MLflow подключается по best effort: его сбой фиксируется в report и логах, но не останавливает публикацию локально валидной модели. Метрики процесса сбрасываются при перезапуске, данные и модели сохраняются в bbolt. Локальная панель не заменяет production-систему авторизации.
