# Архитектура

## Поток событий

API проверяет событие. Локально оно сразу записывается в bbolt. В Kafka-режиме producer использует user_id как ключ, ждёт подтверждения брокера, возвращает 202. Consumer последовательно получает сообщения через FetchMessage, записывает события и пользовательский индекс одной транзакцией и только после этого делает CommitMessages.

При сбое после записи, но до commit, Kafka может доставить событие снова. Стабильный event_id и проверка содержимого предотвращают дубль в хранилище. Это at-least-once доставка с идемпотентным сохранением, не распределённая exactly-once транзакция.

Невалидный JSON, некорректные поля или конфликт идентификатора попадают в product-events-dlq. Если запись в DLQ, storage или commit не удалась, consumer останавливает процесс. Он не продолжает более поздними offset, которые могли бы пропустить ошибку. Docker restart либо Kubernetes запускает процесс заново.

## Модель

Каждому пользователю соответствует вектор товаров: просмотры имеют вес 1, покупки 4, накопленные значения преобразуются log1p. Косинус между столбцами товарной матрицы описывает совместное взаимодействие. История ограничена последними 100 событиями пользователя, для товара сохраняется до 50 соседей.

Рекомендации суммируют similarities соседей просмотренных/купленных товаров, взвешенные историей пользователя. Из выдачи исключаются товары из этой ограниченной истории. Для новых пользователей и при нехватке кандидатов используется популярность всего набора. Каталога доступности здесь нет: список товаров формируется из событий.

Это collaborative filtering с явной формулой, не нейросеть. Параметры модели пересчитываются на накопленных событиях.

## Offline-оценка и обновление

События упорядочиваются по timestamp и event_id. Первые примерно 80% образуют train, оставшиеся holdout. События с одинаковой временной меткой не разделяются между частями. Тестовая цель — новая покупка товара, которого не было в train-истории пользователя; пользователю нужны минимум два разных товара в истории.

HitRate@5 — доля оценочных пользователей, для которых хотя бы один новый купленный товар попал в первые пять рекомендаций. Это не конверсия, Recall@5 или NDCG. Неизвестные модели товары не удаляются из целей, поэтому появление новых товаров может снижать метрику.

Если popularity baseline лучше item-to-item, для публикации выбирается popularity. Минимум оценочных пользователей задаёт MIN_EVAL_USERS. Если есть текущая модель и достаточно новых holdout-покупок с timestamp позже её trained_through, обе модели сравниваются на одном наборе этих новых целей. Снижение HitRate более чем на 0.05 сохраняет champion. Когда новых оценочных пользователей мало, сравнение с champion пропускается; остаются проверки достаточности общей оценки и baseline.

После приёмки выбранная стратегия пересчитывается на всех доступных событиях. Таким образом, артефакт serving обучен на большей истории, чем модель offline-оценки. Оценка не является будущим качеством serving; для него нужны онлайн-наблюдения.

## Публикация и откат

Модель сериализуется в JSON, хешируется SHA-256 и проверяется. bbolt одной транзакцией сохраняет неизменяемый артефакт и активный ID. Затем атомарный указатель в памяти переключается на новую модель; текущие запросы могут завершиться со старой версией. При перезапуске активная версия загружается с диска.

Если активный артефакт повреждён, на старте сервис выбирает самую новую валидную сохранённую версию и сохраняет новый active ID. Если валидных версий нет, сервис останавливается с ошибкой. Ручная активация использует ту же проверку хеша и структуры.

Quality gate — защита до публикации. Онлайн-автооткат по уменьшению покупок не реализован, поскольку этот стенд не содержит достоверного эксперимента и статистического мониторинга конверсии.

## MLflow и Airflow

MLflow вызывается из Go по HTTP: найти/создать эксперимент, создать run, отправить метрики и параметры, загрузить model.json/report.json через проксируемые artifacts, завершить run. Ошибка логируется в tracking_error. Основной реестр и serving от MLflow не зависят. Интеграция не использует MLflow Model Registry/aliases.

Встроенный Go ticker запускает обучение с заданным интервалом. Альтернативы — Kubernetes CronJob либо Airflow DAG, вызывающие Go API. Одновременно используйте один механизм. Мьютекс сериализует обучение и откат внутри процесса, bbolt принадлежит одному серверу.
