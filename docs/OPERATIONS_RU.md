# Эксплуатация

## Конфигурация

| Переменная | По умолчанию | Значение |
|---|---|---|
| HTTP_ADDR | 127.0.0.1:8080 | Адрес Go API |
| DATA_DIR | var | Папка recogo.db |
| ADMIN_TOKEN | recogo-local | Токен обучения и активации |
| TRAIN_INTERVAL | 1h | Период переобучения; 0s отключает |
| MIN_EVAL_USERS | 3 | Минимум оценочных пользователей |
| KAFKA_BROKERS | пусто | Список host:port через запятую; пусто = локальный режим |
| KAFKA_TOPIC | product-events | Основной топик |
| KAFKA_DLQ | product-events-dlq | Топик ошибочных событий |
| MLFLOW_TRACKING_URI | пусто | HTTP URL MLflow; пусто отключает трекинг |
| RECOGO_URL | http://127.0.0.1:8080 | URL для CLI |

Переменные сервера применяются при старте. Токен CLI берёт из окружения или `--token`; URL — из RECOGO_URL или `--url`.

## Метрики и логи

`/metrics` выдаёт количество сохранённых событий, флаг наличия модели, счётчики успешных/неуспешных обучений и откатов, timestamps обучения и принятия модели. Это Prometheus exposition format; отдельный Prometheus/Alertmanager здесь не разворачивается. Настройте внешний сбор и доставку уведомлений, если нужно.

Счётчики относятся к текущему процессу и сбрасываются при рестарте. Постоянная история моделей хранится в bbolt, последний завершённый отчёт — `/report`. Низкоуровневая ошибка до формирования отчёта попадает в JSON-логи и счётчик ошибок; `/report` сохраняет предыдущий завершённый отчёт.

`GET /healthz` подтверждает работу HTTP-процесса, `GET /readyz` — наличие модели. Kafka consumer при существенной ошибке завершает процесс; Compose restart/Kubernetes восстанавливает его. Нет автоматического восстановления потерянной Kafka-истории после истечения retention.

## Резервное копирование

Для простого согласованного backup остановите Go-сервис и скопируйте весь DATA_DIR. При остановленном процессе bbolt-файл содержит события, пользовательский индекс, версии и active ID. В Docker дополнительно сохраняйте volumes Kafka и MLflow. В production используйте штатные snapshot/backup-механизмы и проверяйте восстановление.

`docker compose down` сохраняет volumes. `docker compose down -v` удаляет данные — применяйте только для осознанного полного сброса.

## Надёжность и пределы

Не повышайте replicas у текущего Deployment. Для масштабирования перенесите события и реестр в центральное транзакционное хранилище, отделите consumer/trainer от serving, храните артефакты в объектном хранилище и используйте централизованную координацию публикации.

Лимит 100 000 событий ограничивает учебный стенд, но не гарантирует конкретное время обучения: оно зависит от числа пользователей и их истории. Все события остаются на диске; ограничение 100 используется только для пользовательских векторов, не удаляет записи. На достигнутом лимите потребление прекращается с ошибкой, а offset не подтверждается. Для продолжения нужны архивирование и реализация retention либо другой storage backend.

Нагрузка, доступность Kubernetes, реальный кластер Kafka и показатели бизнеса отдельно не тестировались. Для production также нужны каталог товаров, фильтры наличия, время жизни событий, защита от повторов с конфликтами, доступы Kafka/TLS, мониторинг consumer lag, корректный эксперимент и критерии онлайн-отката.
